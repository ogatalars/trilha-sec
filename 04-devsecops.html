DevSecOps: segurança no pipeline

Ao fim desta página você vai saber que controle de segurança colocar em cada etapa do pipeline, montar um workflow de GitHub Actions com scanners gratuitos e tratar os achados sem travar o time.

O que é DevSecOps

DevSecOps é a prática de colocar segurança dentro do fluxo de entrega de software que já existe (DevOps), em vez de tratá-la como uma auditoria no final. Na prática, é automação: scanners rodando no CI, políticas como código, dependências atualizadas por robôs, imagens assinadas. O papel da pessoa de DevSecOps é escolher esses controles, integrá-los ao pipeline, ajustar para não gerar ruído e ajudar os times a corrigir o que eles acham.

Um pipeline aqui é a esteira automatizada que leva o código do commit até produção: CI (Continuous Integration, integração contínua, que compila e testa a cada mudança) e CD (Continuous Delivery/Deployment, que publica a versão aprovada).

Por que isso importa para quem vem de dev

Você já escreve workflow de CI, já mexeu em Dockerfile, já sofreu com teste quebrado bloqueando merge. DevSecOps é exatamente isso, com outro tipo de verificação. A habilidade rara no mercado não é "saber rodar o Trivy" (qualquer um roda); é saber colocar o scanner sem que o time passe a odiá-lo: escolher o que bloqueia, o que só avisa, e como fazer a correção caber no fluxo normal de PR. Isso é engenharia, e você já sabe fazer.

Shift left: o que é e onde para

Shift left ("mover para a esquerda") é a ideia de achar problemas mais cedo na linha do tempo do desenvolvimento. Se você desenhar o ciclo da esquerda (ideia, código) para a direita (produção), mover segurança para a esquerda significa pegar a falha no editor ou no PR, e não depois do deploy. O motivo é custo: corrigir um SQL injection apontado no PR leva minutos; corrigir o mesmo bug depois de um vazamento envolve incidente, comunicação a clientes e às vezes multa.

Mas shift left tem limites, e quem vende a ideia esquece de dizer:

  • Nem tudo é visível no código. Configuração de produção, permissão real na nuvem e comportamento em execução só aparecem à direita. Por isso existe o complemento, às vezes chamado de shift right: monitoramento e detecção em runtime.
  • Ferramenta não substitui desenho. Nenhum scanner acha falha de lógica de negócio, como "o cupom pode ser aplicado duas vezes", nem a maioria dos IDORs. Threat modeling e revisão humana (página anterior) continuam necessários.
  • Empurrar tudo para o dev não é shift left, é transferir trabalho. Se o pipeline despeja 400 alertas no PR, o time aprende a ignorar. O objetivo é dar ao dev poucos achados, relevantes e com a correção clara.

SAST: análise estática do código

SAST (Static Application Security Testing) analisa o código-fonte sem executá-lo, procurando padrões perigosos. O tipo mais útil faz taint analysis (análise de contaminação): marca dados vindos do usuário como "contaminados" (a source) e avisa se eles chegam a uma função perigosa (o sink, como cursor.execute) sem passar por um tratamento.

  • Semgrep: regras escritas em algo parecido com o próprio código, rápido, roda local e no CI. Versão de linha de comando open source; tem registro público de regras. Fácil de escrever regra própria para um padrão da sua empresa.
  • CodeQL: do GitHub. Transforma o código num banco de dados consultável e roda queries de fluxo de dados mais profundas. Gratuito em repositórios públicos; em privados exige licença (GitHub Advanced Security / Code Security).
# Exemplo de regra Semgrep: proíbe requests sem timeout
rules:
  - id: requests-sem-timeout
    languages: [python]
    severity: WARNING
    message: "requests sem timeout pode travar o worker indefinidamente"
    patterns:
      - pattern: requests.$METHOD(...)
      - pattern-not: requests.$METHOD(..., timeout=$T, ...)

Limite: SAST gera falsos positivos (alertas sobre algo que não é problema de verdade, por exemplo porque a validação acontece num lugar que a ferramenta não enxerga) e falsos negativos (problemas reais que ele não vê, como falhas de autorização). Comece com um conjunto pequeno de regras de alta confiança.

SCA: dependências vulneráveis

Seu código é uma fração pequena do que roda: o resto são bibliotecas. SCA (Software Composition Analysis) lê o seu arquivo de dependências (package-lock.json, poetry.lock, go.sum) e cruza cada versão com bancos de vulnerabilidades conhecidas. Cada vulnerabilidade pública recebe um CVE (Common Vulnerabilities and Exposures, identificador único como CVE-2021-44228, o Log4Shell) e normalmente uma nota CVSS (Common Vulnerability Scoring System, de 0 a 10, que estima a gravidade técnica).

  • Dependabot: embutido no GitHub. Alerta sobre dependência vulnerável e abre PR com a versão corrigida. Também pode abrir PRs de atualização de rotina.
  • Trivy: scanner multiuso da Aqua Security; com trivy fs . lê os lockfiles do projeto.
  • OSV-Scanner: do Google, usa o banco aberto OSV.dev, que agrega avisos de vários ecossistemas.

Detalhe importante: dependência vulnerável não significa aplicação vulnerável. Se o CVE está numa função da biblioteca que você nunca chama, o risco real é baixo. Algumas ferramentas fazem reachability analysis (verificam se o código vulnerável é de fato alcançável a partir do seu), o que reduz muito o ruído. Use o lockfile sempre: sem ele, o scanner não sabe a versão exata instalada.

Secret scanning

Como vimos na página anterior, segredo commitado é segredo vazado. O scanner procura padrões conhecidos (formato de chave AWS, token do GitHub, chave privada) e strings de alta entropia (aleatoriedade, típica de tokens).

  • gitleaks: open source, roda como hook de pre-commit (na máquina do dev, antes do commit existir), no CI e também no histórico inteiro do repositório (gitleaks git), útil para auditar repositórios antigos.
  • GitHub push protection: o próprio GitHub recusa o git push se detectar um segredo de formato conhecido. Ativo por padrão para usuários em repositórios públicos; em organizações com repositórios privados depende do plano.
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.2   # fixe a versão; confira a mais recente
    hooks:
      - id: gitleaks
Armadilha comum

Achou um segredo no histórico? Rotacione primeiro. Reescrever o histórico (com git filter-repo) é opcional e não adianta sozinho: forks, clones e caches já têm a chave.

DAST: testando a aplicação rodando

DAST (Dynamic Application Security Testing) testa a aplicação em execução, de fora, como um atacante faria: manda requisições e analisa respostas. Enxerga coisas que o SAST não vê, como cabeçalhos de segurança ausentes, cookies sem Secure, páginas de erro com stack trace e configuração do servidor.

A ferramenta gratuita de referência é o ZAP (antes OWASP ZAP, hoje mantido como ZAP by Checkmarx, ainda open source). Ele tem dois modos: baseline (passivo, só observa respostas; seguro e rápido, bom para PR) e full scan (ativo, envia payloads de ataque; mais lento e pode sujar dados, então rode só contra staging, nunca produção).

docker run --rm -t ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t https://staging.exemplo.com

IaC scanning

IaC (Infrastructure as Code, infraestrutura como código) é descrever a infraestrutura em arquivos versionados: Terraform, manifests de Kubernetes, CloudFormation, Helm charts. A vantagem para segurança é enorme: a configuração pode ser revisada e escaneada no PR, antes de existir. É aqui que se pega a categoria A02 do Top 10 (Security Misconfiguration).

  • Checkov: da Palo Alto (Prisma Cloud), open source, centenas de políticas prontas para Terraform, Kubernetes, Dockerfile e outros.
  • Trivy config: trivy config . faz o mesmo, aproveitando a ferramenta que você já usa para imagens.
# Terraform que um scanner de IaC vai apontar
resource "aws_security_group_rule" "ssh" {
  type        = "ingress"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]   # SSH aberto para a internet inteira
}

Container scanning e hardening de imagem

Uma imagem de container carrega um sistema operacional mínimo com dezenas ou centenas de pacotes, e cada um pode ter CVEs. Container scanning é listar esses pacotes e cruzar com bancos de vulnerabilidades: trivy image minha-app:1.4.0. Mas reduzir o que está na imagem é mais eficaz do que escanear: pacote que não existe não tem CVE. Isso é hardening (endurecimento: remover o desnecessário e restringir o que sobra).

# ANTES: imagem grande, roda como root, tag móvel
FROM python:3.12
COPY . /app
RUN pip install -r /app/requirements.txt
CMD ["python", "/app/main.py"]

# DEPOIS: multi-stage, distroless, não-root, base fixada por digest
FROM python:3.12-slim@sha256:<digest> AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --target=/deps -r requirements.txt
COPY . .

FROM gcr.io/distroless/python3-debian12:nonroot@sha256:<digest>
WORKDIR /app
COPY --from=build /deps /deps
COPY --from=build /app /app
ENV PYTHONPATH=/deps
USER nonroot
CMD ["main.py"]
  • Distroless: imagens do Google que contêm só o runtime da linguagem, sem shell nem gerenciador de pacotes. Menos CVEs e, se alguém invadir o container, não tem bash nem curl à mão. Alternativas parecidas: Chainguard images, Alpine (menor, mas com shell).
  • Não-root: se o processo for comprometido, roda sem privilégios. Em Kubernetes, reforce com runAsNonRoot: true.
  • .dockerignore: o COPY . . do estágio de build copia tudo o que está na pasta, inclusive .env e .git, e o COPY --from=build /app /app leva isso para a imagem final. Crie um .dockerignore com .git, .env e afins, ou copie só os arquivos da aplicação. E alinhe a versão do Python da imagem de build com a da imagem final, porque pacotes compilados dependem dela.
  • Fixar por digest: a tag python:3.12 é um ponteiro que muda; o digest sha256:... é o hash do conteúdo e identifica exatamente uma imagem. Fixar por digest garante build reprodutível e impede que uma tag adulterada entre no seu build. O Dependabot e o Renovate atualizam digests automaticamente via PR. (Atenção: o caminho exato da imagem distroless de Python e suas variantes mudam com as versões do Debian; confira no repositório GoogleContainerTools/distroless.)

Cadeia de suprimentos de software

Supply chain security (segurança da cadeia de suprimentos) cuida de tudo que entra no seu software sem ser escrito por você: dependências, imagens base, ferramentas de build, actions do CI. Os casos que tornaram o tema famoso: SolarWinds (2020, o servidor de build foi invadido e o malware entrou no produto assinado), o backdoor no xz-utils (2024, um mantenedor "confiável" inseriu código malicioso ao longo de anos) e o comprometimento da action tj-actions/changed-files (2025, a tag foi movida para código que vazava segredos nos logs de CI). Desde 2025 é a categoria A03 do OWASP Top 10.

SBOM

Um SBOM (Software Bill of Materials, lista de materiais do software) é um inventário legível por máquina de todos os componentes de um artefato, com nome e versão. Serve para responder em minutos a pergunta que todo mundo fez no Log4Shell: "onde, na empresa, usamos log4j 2.14?". Os dois formatos padrão são CycloneDX (da OWASP) e SPDX (da Linux Foundation, também norma ISO). Syft (da Anchore) gera SBOM de diretórios e imagens: syft minha-app:1.4.0 -o cyclonedx-json > sbom.json. O Trivy também gera.

SLSA em palavras simples

SLSA (Supply-chain Levels for Software Artifacts, pronuncia-se "salsa") é um framework que define níveis de garantia sobre como um artefato foi construído. A peça central é a proveniência (provenance): um documento que diz "este binário foi gerado a partir deste commit, por este sistema de build, com estes parâmetros". Na versão 1.0, a trilha de build tem estes níveis:

  • Nível 0: nenhuma garantia.
  • Nível 1: existe proveniência, gerada pelo processo de build. Ajuda a saber de onde veio, mas pode ser forjada.
  • Nível 2: o build roda numa plataforma hospedada (como o GitHub Actions), que assina a proveniência. Adulterar depois do build passa a ser detectável.
  • Nível 3: a plataforma de build é endurecida: builds isolados entre si e os segredos de assinatura inacessíveis ao código do projeto, então nem um passo malicioso do build consegue forjar a proveniência.

No GitHub, a action actions/attest-build-provenance gera proveniência assinada com pouco esforço.

Assinatura com Sigstore e cosign

Sigstore é um projeto aberto (da OpenSSF) para assinar artefatos sem precisar gerenciar chaves de longa duração. O cosign é a ferramenta dele para imagens de container. No modo keyless, o CI se identifica via OIDC (OpenID Connect, protocolo em que um provedor, aqui o GitHub, emite um token que prova "sou o workflow X do repositório Y"), recebe um certificado de curta duração e a assinatura fica registrada num log público e auditável (Rekor). No deploy, você verifica que a imagem foi assinada por aquele workflow específico:

cosign sign ghcr.io/org/app@sha256:<digest>

cosign verify ghcr.io/org/app@sha256:<digest> \
  --certificate-identity 'https://github.com/org/app/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Use a identidade exata, com o arquivo do workflow e a branch. Um regex aberto como ^https://github.com/org/app/ aceitaria a assinatura de qualquer workflow, em qualquer branch, desse repositório.

GitHub Actions: o próprio CI é superfície de ataque

O workflow do CI roda com acesso a segredos e permissão de escrita no repositório. Três cuidados resolvem a maior parte do risco:

  1. Fixar actions por SHA de commit. uses: actions/checkout@v4 aponta para uma tag, e tags podem ser movidas por quem controla o repositório da action (foi o que aconteceu no caso tj-actions, em 2025, e de novo em 19/03/2026 com o aquasecurity/trivy-action, a mesma action do exemplo abaixo: 76 das 77 tags foram reapontadas para código que roubava credenciais, e a própria Aqua escreveu que fixar pelo SHA completo é a única proteção confiável). O SHA completo do commit é imutável. Mantenha o comentário com a versão e deixe o Dependabot atualizar.
  2. Privilégio mínimo no GITHUB_TOKEN. Todo job recebe um token automático; dependendo da configuração da organização, ele pode ter escrita em tudo. Declare permissions: no topo do workflow com o mínimo (em geral contents: read) e eleve só no job que precisa.
  3. Cuidado com pull_request_target. Diferente de pull_request, esse evento roda no contexto do repositório de destino, com acesso a segredos e token com escrita, mesmo para PRs vindos de forks. Se o workflow fizer checkout do código do PR e executá-lo (instalar dependências, rodar testes, build), qualquer pessoa na internet abre um PR e roda código com seus segredos. Essa classe de ataque é chamada de "pwn request". Regra: não use pull_request_target para nada que execute código do PR.
on: pull_request_target
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}   # código do fork
      - run: npm install && npm test                      # executa com seus segredos

Outro cuidado relacionado é script injection em workflow: interpolar ${{ github.event.pull_request.title }} direto num run: deixa o título do PR virar comando de shell. Passe esses valores por variável de ambiente (env:) e use "$TITULO" no script.

Exemplo completo: workflow de segurança no GitHub Actions

Este workflow roda gitleaks, Semgrep e Trivy a cada PR e push na main. As três ferramentas são gratuitas, e o GitHub Actions é gratuito em repositórios públicos (privados têm uma cota de minutos por mês). Os resultados de Semgrep e Trivy vão para a aba Security do GitHub no formato SARIF (Static Analysis Results Interchange Format, um JSON padrão para resultados de ferramentas de análise), que mostra os achados como anotações no PR. O upload de SARIF para o code scanning é gratuito em repositórios públicos.

# .github/workflows/security.yml
name: security

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read            # padrão mínimo para todos os jobs

jobs:
  gitleaks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<SHA-de-40-caracteres>   # v4
        with:
          fetch-depth: 0      # histórico completo para varrer os commits do PR
          persist-credentials: false   # o token não fica salvo no .git/config
      - name: gitleaks
        run: |
          docker run --rm -v "$PWD:/repo" ghcr.io/gitleaks/gitleaks:v8.21.2@sha256:<digest> \
            git /repo --redact --verbose

  semgrep:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write   # só este job pode enviar SARIF
    container:
      image: semgrep/semgrep:<versão>@sha256:<digest>   # imagem de terceiro: fixe por digest
    steps:
      - uses: actions/checkout@<SHA-de-40-caracteres>   # v4
        with:
          persist-credentials: false
      - run: semgrep scan --config p/default --sarif --output semgrep.sarif
      - uses: github/codeql-action/upload-sarif@<SHA>    # v3
        if: always()
        with:
          sarif_file: semgrep.sarif
          category: semgrep

  trivy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@<SHA-de-40-caracteres>   # v4
        with:
          persist-credentials: false
      - name: Trivy (dependências e IaC do repositório)
        uses: aquasecurity/trivy-action@<SHA>            # fixe por SHA
        with:
          scan-type: fs
          scanners: vuln,misconfig
          severity: CRITICAL,HIGH
          ignore-unfixed: true      # só alerta o que já tem correção
          format: sarif
          output: trivy.sarif
      - uses: github/codeql-action/upload-sarif@<SHA>    # v3
        if: always()
        with:
          sarif_file: trivy.sarif
          category: trivy
      - name: Falhar só em CRITICAL com correção disponível
        uses: aquasecurity/trivy-action@<SHA>
        with:
          scan-type: fs
          scanners: vuln
          severity: CRITICAL
          ignore-unfixed: true
          exit-code: "1"

Pontos de design que valem explicar:

  • Placeholders <SHA>: substitua pelo SHA completo do commit da release que você escolheu (aparece na página de releases da action). Não copie SHAs de tutoriais sem conferir. O Dependabot, configurado com package-ecosystem: github-actions, mantém esses SHAs atualizados.
  • persist-credentials: false e imagens por digest: por padrão o actions/checkout grava o token no .git/config, ao alcance de qualquer container ou script que rode depois no mesmo job. E as imagens de terceiros (Semgrep, gitleaks) seguem a mesma regra das actions: tag pode ser movida, digest não.
  • Gitleaks via container: a action oficial do gitleaks exige licença gratuita para repositórios de organizações; rodar a imagem diretamente evita isso. Confira a versão mais recente da imagem.
  • Relatar tudo, bloquear pouco: o primeiro passo do Trivy envia HIGH e CRITICAL para a aba Security; o segundo só falha o build em CRITICAL que já tem correção. Isso é política, não detalhe técnico, e é o assunto da próxima seção.
  • Semgrep: p/default é um conjunto público de regras; depois você troca por um conjunto adaptado à sua stack (por exemplo p/python, p/owasp-top-ten). Ele não falha o build por padrão com --sarif; adicione --error quando o ruído estiver sob controle.

Triagem: o trabalho de verdade

Rodar scanner é fácil; o que diferencia um bom programa de DevSecOps é o que se faz com os resultados. Triagem é decidir, para cada achado: é real? É relevante no nosso contexto? Qual a prioridade? Quem corrige?

Falsos positivos

Quando um achado não é real, registre o motivo junto do código, para que a decisão seja revisável no PR: # nosemgrep: regra-x -- valor vem de enum interno, ou um arquivo .trivyignore com o CVE e uma data de expiração. Supressão sem justificativa e sem prazo vira cemitério de alertas. Se uma regra gera falso positivo com frequência, ajuste ou desligue a regra: alerta que ninguém lê é pior que nenhum, porque dá falsa sensação de cobertura.

Severidade de verdade

O CVSS mede gravidade técnica no pior cenário, não o risco para você. Para priorizar, combine com contexto:

  • Exposição: o serviço é acessível pela internet ou só interno?
  • Alcance: o código vulnerável é chamado?
  • Exploração real: o CVE está no catálogo KEV da CISA (Known Exploited Vulnerabilities, lista de falhas que comprovadamente estão sendo exploradas)? O EPSS (Exploit Prediction Scoring System, probabilidade estimada de exploração nos próximos 30 dias) está alto?
  • Dados: o sistema guarda dado pessoal, financeiro, credenciais?

SLA de correção

Um SLA (Service Level Agreement, acordo de nível de serviço) de correção é o prazo máximo que a empresa se compromete a levar para corrigir uma vulnerabilidade, conforme a severidade. Ele transforma "corrigir quando der" em algo mensurável. Os números variam por empresa e por exigências de compliance; um exemplo de política razoável para começar:

Severidade (após triagem)Prazo de exemploBloqueia o merge?
Crítica, exposta à internet ou no KEV7 dias (ou imediato, se em exploração ativa)Sim, quando há correção disponível
Alta30 diasNão; vira card com prazo
Média90 diasNão
BaixaMelhor esforço, revisada no ciclo de atualizaçãoNão

Não bloqueie tudo

A tentação de quem começa é fazer o pipeline falhar em qualquer achado. O resultado é previsível: o time pede exceção, desliga o job ou cria um || true. Estratégias que funcionam melhor:

  • Comece em modo de relatório, sem bloquear, por algumas semanas; meça o ruído e ajuste as regras.
  • Bloqueie só o que é novo (diff-aware): o PR não pode introduzir problema crítico, mas o legado é tratado num backlog com SLA. O Semgrep faz isso nativamente em PR.
  • Bloqueie o que tem alta confiança e correção fácil: segredo vazado, CVE crítico com versão corrigida, Terraform com bucket público.
  • Tenha um caminho de exceção documentado, com dono e prazo, em vez de exceção informal.

Kubernetes: segurança em três palavras

Se sua empresa roda em Kubernetes (orquestrador que distribui containers entre máquinas e os mantém rodando), três controles nativos aparecem em toda revisão. Aqui vai só o mapa; uma parte futura da trilha aprofunda segurança de nuvem e Kubernetes.

  • RBAC (Role-Based Access Control): define quem (pessoa ou service account de um pod) pode fazer o que com quais recursos da API do cluster. Erro comum: dar cluster-admin para o pipeline de deploy ou para um pod que só precisava ler um ConfigMap.
  • Pod Security Standards: três perfis oficiais (privileged, baseline, restricted) que limitam o que um pod pode pedir: rodar como root, montar diretórios do host, usar rede do host. São aplicados por namespace via um rótulo, como pod-security.kubernetes.io/enforce: restricted.
  • NetworkPolicy: regras de firewall entre pods. Por padrão, todo pod fala com todo pod; uma política de negar tudo e liberar só os fluxos necessários limita o estrago se um serviço for invadido (movimento lateral).

Métricas: como saber se está funcionando

Um programa de DevSecOps precisa mostrar resultado com números, não com quantidade de ferramentas. Ideias de métricas:

  • MTTR de vulnerabilidade (Mean Time To Remediate, tempo médio entre a detecção e a correção), separado por severidade. É a métrica principal: mostra se os achados viram correção.
  • Cumprimento de SLA: percentual de vulnerabilidades corrigidas dentro do prazo, e quantas estão vencidas hoje.
  • Cobertura: percentual de repositórios com os scanners ativos, com push protection ligada, com permissions: declarado.
  • Taxa de falso positivo por regra ou ferramenta: indica onde ajustar.
  • Segredos detectados antes do push vs. depois: se o pre-commit funciona, o número "depois" cai.
  • Idade das imagens em produção: imagens antigas acumulam CVEs novos mesmo sem mudança de código.
Armadilha comum

"Número de vulnerabilidades encontradas" sozinho é uma métrica ruim: sobe quando você adiciona um scanner novo (o que é bom) e cai quando alguém desliga um (o que é péssimo). Prefira métricas de fluxo, como MTTR e cumprimento de SLA.

E com IA?
  • Pacotes que não existem. Assistentes de código sugerem dependências inventadas: num estudo publicado no USENIX Security 2025, 19,7% dos pacotes sugeridos não existiam. Um atacante pode registrar esses nomes (slopsquatting). O SCA no PR e a pergunta "esse pacote existe, e quem publica?" resolvem boa parte.
  • Código gerado passa pelo mesmo pipeline. Num estudo do IEEE S&P 2022, cerca de 40% do código gerado pelo Copilot em cenários de risco era vulnerável. SAST, SCA e revisão humana valem igual, e alguém do time responde pelo merge.
  • Modelos e servidores MCP são dependências. Fixe versão e hash, revise que ferramentas cada servidor expõe e rode com o mínimo de permissão.
  • Agente no CI é alvo de prompt injection. Um agente que lê issues e PRs de terceiros pode receber instruções escondidas nesse texto. Dê permissions: mínimas ao job e não exponha segredos a ele.
  • Segredo não vai para o prompt, nem para os arquivos de contexto do agente. Inclua esses arquivos no secret scanning.

Qual a diferença entre SAST, SCA e DAST, e em que etapa do pipeline cada um rende mais?

SAST analisa o seu código-fonte sem executá-lo (PR). SCA verifica as versões das dependências contra bancos de CVEs (PR e continuamente, porque CVEs novos surgem em versões antigas). DAST testa a aplicação rodando, de fora (staging, após o deploy).

Por que fixar uma action por SHA de commit em vez de @v4?

Tags são ponteiros que podem ser movidos por quem controla o repositório da action; se ele for comprometido, a tag pode passar a apontar para código malicioso (caso tj-actions, 2025). O SHA é imutável. O Dependabot atualiza os SHAs via PR.

O que torna pull_request_target perigoso?

Ele roda no contexto do repositório de destino, com segredos e token com escrita, mesmo para PRs de forks. Se o workflow fizer checkout e executar o código do PR, qualquer pessoa consegue rodar código com seus segredos ("pwn request").

Um CVE de CVSS 9.8 aparece numa biblioteca de um serviço interno, numa função que o código nunca chama. Ele deve bloquear o deploy?

Provavelmente não. Depois da triagem (sem exposição à internet, código não alcançável), a severidade real é menor; vira card com prazo de SLA. Bloqueio fica para o que é crítico de verdade e tem correção, e a decisão fica registrada com justificativa.

Cite três mudanças que endurecem uma imagem de container e o porquê de cada uma.

Usar base distroless ou mínima (menos pacotes, menos CVEs, sem shell para o atacante); rodar como usuário não-root (processo comprometido sem privilégios); fixar a base por digest (build reprodutível e imune a tag adulterada). Multi-stage build também ajuda, deixando compiladores fora da imagem final.
