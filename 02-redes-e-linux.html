Redes e Linux para segurança

Ao fim desta página você vai entender o caminho de uma requisição pela rede, saber quais cabeçalhos HTTP protegem sua aplicação e conseguir investigar um servidor Linux com os comandos que um analista de segurança usa.

Por que isso importa para quem vem de dev

Como dev, você usa a rede através de abstrações: um fetch(), um driver de banco, um docker compose up. Em segurança, os ataques e as evidências moram justamente embaixo dessas abstrações: uma porta de Redis aberta para a internet, um DNS adulterado, um login SSH suspeito às 3h da manhã no auth.log. Quase todo servidor que você vai defender roda Linux, e quase todo incidente deixa rastro na rede ou nos logs. Esta página é o mínimo para enxergar esse andar de baixo.

O modelo em camadas

Redes são organizadas em camadas: cada uma resolve um problema e usa a de baixo sem precisar saber como ela funciona — igual às camadas de uma aplicação (controller, service, repository). O modelo prático é o TCP/IP, com quatro camadas:

CamadaO que resolveExemplos
AplicaçãoO "assunto" da conversaHTTP, DNS, SSH, protocolo do Postgres
TransporteEntregar dados ao programa certo, com ou sem garantiaTCP, UDP
Internet (rede)Levar pacotes até a máquina certa, atravessando roteadoresIP, ICMP (o do ping)
Enlace / físicaMover bits no meio físico localEthernet, Wi-Fi

Você também vai ouvir falar do modelo OSI, um modelo de referência com sete camadas. Não precisa decorá-lo, mas a numeração dele virou jargão: "ataque de camada 7" é na aplicação (HTTP), "firewall de camada 4" olha IP e porta. Basta saber que 7 = aplicação, 4 = transporte e 3 = rede.

IP, porta, TCP e UDP

Um endereço IP identifica uma máquina (ou interface de rede) — por exemplo 192.168.0.10 no IPv4. Uma porta é um número de 0 a 65535 que identifica qual programa naquela máquina recebe os dados. A combinação IP + porta (10.0.0.5:5432) é o endereço completo de um serviço. Portas abaixo de 1024 são "privilegiadas": no Linux, tradicionalmente só o root pode abri-las.

Na camada de transporte há dois protocolos principais:

  • TCP (Transmission Control Protocol): orientado a conexão, garante entrega e ordem, reenvia o que se perde. Usado por HTTP/1.1, HTTP/2, SSH, bancos de dados.
  • UDP (User Datagram Protocol): manda e esquece, sem conexão nem garantia. Mais leve e rápido. Usado por DNS (na maioria das consultas), streaming, jogos e pelo HTTP/3 (via QUIC).

O handshake TCP

Antes de trocar dados, o TCP abre a conexão com o three-way handshake (aperto de mão em três etapas):

cliente  ── SYN ──────────▶  servidor   # "quero conectar"
cliente  ◀── SYN-ACK ─────  servidor   # "ok, aceito"
cliente  ── ACK ──────────▶  servidor   # "confirmado, conexão aberta"

Por que isso importa para segurança? Porque é assim que ferramentas descobrem portas abertas: se a resposta ao SYN é SYN-ACK, há um serviço escutando. E também porque o ataque SYN flood abusa disso: manda milhares de SYN e nunca completa, ocupando recursos do servidor até ele não aceitar conexões legítimas (um ataque à disponibilidade).

DNS: a agenda telefônica da internet

O DNS (Domain Name System) traduz nomes como api.exemplo.com em endereços IP. Seu computador pergunta a um resolvedor (do provedor, da empresa ou público, como 1.1.1.1), que consulta os servidores responsáveis pelo domínio e guarda a resposta em cache por um tempo (o TTL, time to live). Tipos de registro comuns: A (IPv4), AAAA (IPv6), CNAME (apelido para outro nome), MX (servidor de e-mail), TXT (texto livre, usado para verificação de domínio e políticas de e-mail).

Por que DNS é assunto de segurança: quem controla a resposta do DNS controla para onde você vai. Alguns ataques:

  • DNS spoofing / cache poisoning: o atacante faz um resolvedor guardar uma resposta falsa, mandando usuários para um IP dele. O TLS ajuda aqui: o servidor falso não terá certificado válido para o domínio. O DNSSEC é uma extensão que assina as respostas DNS para detectar adulteração.
  • Subdomain takeover: um registro CNAME aponta para um recurso de cloud que foi apagado (um app, um bucket), e um atacante cria um recurso com o mesmo nome, passando a servir conteúdo no seu subdomínio.
  • DNS também é usado por malware para exfiltrar dados (vazar informação para fora) escondidos em consultas, porque quase nenhuma rede bloqueia DNS.

HTTP, HTTPS e cabeçalhos de segurança

HTTPS é HTTP dentro de TLS (visto na página anterior). Além disso, o navegador obedece a alguns cabeçalhos de resposta que ativam proteções. São baratos de configurar e reduzem classes inteiras de ataque:

Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self'
X-Content-Type-Options: nosniff
Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/
  • HSTS (Strict-Transport-Security): diz ao navegador "durante este tempo, só fale comigo via HTTPS". Impede que um atacante na rede rebaixe a conexão para HTTP.
  • CSP (Content-Security-Policy): lista de onde a página pode carregar scripts, estilos e outros recursos. Se um atacante conseguir injetar um <script> (ataque chamado XSS, cross-site scripting), uma CSP restritiva pode impedir que ele rode.
  • X-Content-Type-Options: nosniff: impede o navegador de "adivinhar" o tipo de um arquivo e, por exemplo, executar como script um upload que deveria ser texto.

Os atributos de cookie merecem atenção especial, porque o cookie de sessão é a chave da conta do usuário:

AtributoO que fazProtege contra
SecureCookie só é enviado por HTTPSRoubo do cookie em rede insegura
HttpOnlyJavaScript não consegue ler o cookie (document.cookie)XSS roubando a sessão
SameSiteStrict ou Lax limitam o envio do cookie em requisições vindas de outros sites; None libera (e exige Secure)CSRF (cross-site request forgery): outro site fazendo o navegador da vítima disparar ações na sua aplicação
Ponte com o que você já faz

Esses cabeçalhos geralmente são uma linha no seu framework ou no proxy: middlewares como helmet no Express, configurações de sessão no Django/Rails/Spring, ou add_header no nginx. Abra o DevTools, aba Network, clique numa resposta da sua aplicação e confira quais deles estão lá.

Firewall, NAT, VPN, proxy reverso e WAF

  • Firewall: filtra tráfego por regras, tipicamente por IP, porta e protocolo ("só aceite 443 de qualquer lugar e 22 da rede do escritório"). Os security groups da AWS e as regras de firewall de VPC do GCP são firewalls. No Linux, iptables/nftables e o ufw (uma interface simplificada).
  • NAT (Network Address Translation): traduz endereços privados (10.x, 192.168.x) para um IP público. É o que seu roteador de casa faz. Como efeito colateral, máquinas atrás do NAT não recebem conexões de fora por padrão — mas NAT não é firewall, e não deve ser tratado como controle de segurança.
  • VPN (Virtual Private Network): um túnel cifrado que coloca sua máquina "dentro" de outra rede. Útil para acessar recursos privados; no modelo zero trust, estar na VPN não deveria bastar para ter acesso a tudo.
  • Proxy reverso: um servidor que fica na frente das aplicações, recebe as requisições e as repassa (nginx, Envoy, um load balancer de cloud). Concentra TLS, cabeçalhos e limites num ponto só.
  • WAF (Web Application Firewall): um filtro de camada 7 que inspeciona o conteúdo HTTP e bloqueia padrões de ataque conhecidos (como ' OR 1=1--). Exemplos: Cloudflare WAF, AWS WAF, ModSecurity.
Armadilha comum

Tratar o WAF como substituto de código seguro. Ele é uma camada extra (defesa em profundidade), não a correção: regras de WAF são contornáveis com variações de payload, e ele não enxerga falhas de lógica, como um usuário acessando o pedido de outro.

Ferramentas de rede

  • curl -v: mostra a conversa inteira — resolução, handshake TLS, certificado, cabeçalhos enviados e recebidos. É o primeiro passo para ver se aqueles cabeçalhos de segurança estão mesmo lá.
  • dig: consulta DNS diretamente. dig exemplo.com A, dig exemplo.com MX, dig +short para só a resposta.
  • ss (substituto moderno do netstat): lista conexões e portas abertas na sua máquina. ss -tulpn = TCP, UDP, só portas em escuta (listening), com o processo dono, sem resolver nomes.
  • nmap: scanner de rede que descobre máquinas, portas abertas e versões de serviços. Ferramenta padrão de pentest e de auditoria.
  • tcpdump e Wireshark: capturam os pacotes que passam pela interface de rede. O tcpdump roda no terminal (bom para servidores); o Wireshark tem interface gráfica e decodifica centenas de protocolos. Ambos precisam de privilégio.
Atenção à lei

Use nmap e afins só no seu próprio laboratório ou em sistemas com autorização por escrito. Escanear ou tentar acessar sistemas de terceiros sem autorização pode ser enquadrado como crime no Brasil — a Lei 12.737/2012 (conhecida como "Lei Carolina Dieckmann") tipificou a invasão de dispositivo informático — além de violar termos de uso de provedores. Para treinar, há alvos feitos para isso, como scanme.nmap.org (liberado pelo próprio projeto Nmap para scans leves) e plataformas como TryHackMe e Hack The Box.

Linux para segurança

Usuários, grupos e permissões

No Linux, todo arquivo tem um dono (usuário), um grupo e três conjuntos de permissões: para o dono, para o grupo e para os outros. Cada conjunto tem r (read, ler), w (write, escrever) e x (execute, executar; em diretório, significa poder entrar nele).

$ ls -l /etc/shadow app.env
-rw-r----- 1 root shadow 1234 nov 20 10:00 /etc/shadow
-rw-r--r-- 1 deploy deploy  88 nov 20 10:00 app.env
# tipo | dono rw- | grupo r-- | outros r--
# app.env com segredos legível por "outros": qualquer usuário da máquina lê

$ chmod 600 app.env     # r=4 w=2 x=1 → 6=rw- para o dono, 0 para o resto
-rw------- 1 deploy deploy  88 nov 20 10:00 app.env

O usuário root (UID 0) pode tudo, ignorando permissões. Por isso o menor privilégio no Linux significa rodar aplicações com um usuário próprio, sem poderes, e não como root — o mesmo motivo de usar USER app no seu Dockerfile.

sudo permite que um usuário rode comandos como root (ou outro usuário), conforme regras em /etc/sudoers, e registra cada uso no log. É melhor que logar como root porque deixa rastro de quem fez o quê. sudo -l mostra o que o seu usuário pode rodar — e é um dos primeiros comandos que um atacante roda ao entrar numa máquina.

SUID: por que é perigoso

O bit SUID (set user ID) faz um executável rodar com as permissões do dono do arquivo, não de quem o executou. Aparece como s no lugar do x:

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 /usr/bin/passwd   # roda como root para poder gravar /etc/shadow

O passwd precisa disso para que você troque a própria senha. O perigo: se um binário SUID de root tiver uma falha, ou permitir rodar comandos arbitrários (como um editor ou interpretador com SUID colocado por engano), qualquer usuário vira root. Isso se chama escalação de privilégio (sair de um usuário comum para um com mais poder), e listar binários SUID com find / -perm -4000 -type f 2>/dev/null é passo padrão tanto do atacante quanto de quem audita.

Processos

Cada programa rodando é um processo, com um PID (identificador), um usuário dono e um processo pai. Investigar processos responde "o que está rodando e como quem?". Um minerador de criptomoeda rodando como www-data (o usuário do servidor web), filho do processo do nginx, é um sinal clássico de aplicação web comprometida.

Logs

Logs são a principal evidência do Blue Team (a equipe que defende e detecta). Os lugares mais importantes:

  • /var/log/: o diretório tradicional de logs.
  • /var/log/auth.log (Debian/Ubuntu, quando o rsyslog está instalado; desde o Debian 12 ele não vem por padrão e esses eventos ficam só no journal) ou /var/log/secure (RHEL/Fedora): logins, falhas de senha, uso de sudo, conexões SSH.
  • journalctl: lê o journal do systemd, o sistema de logs da maioria das distribuições atuais. journalctl -u ssh filtra por serviço; --since "1 hour ago" filtra por tempo.

Comandos de investigação

ComandoPergunta que responde
who / wQuem está logado agora?
lastQuem logou recentemente, de onde e quando?
ps aux / ps -ef --forestQue processos rodam, como qual usuário, e quem é pai de quem?
ss -tulpnQue portas estão abertas e qual processo as abriu?
lsof -i / lsof -p PIDQue conexões de rede e arquivos um processo tem abertos?
grepOnde está aquele IP, usuário ou erro nos logs?

Mini-lab: rode na sua máquina

Tudo abaixo é seguro e toca só na sua máquina ou em consultas públicas normais. Em macOS, alguns comandos mudam (ss não existe; use lsof -iTCP -sTCP:LISTEN). Se puder, faça numa VM ou num container Linux.

# 1. Veja a conversa HTTPS inteira: TLS, certificado, cabeçalhos
curl -v https://github.com -o /dev/null 2>&1 | grep -Ei "SSL|subject|issuer|strict-transport|^< "

# 2. Consulte o DNS
dig +short github.com A
dig github.com MX

# 3. Quais portas sua máquina está escutando, e qual processo?
sudo ss -tulpn

# 4. Scan na SUA máquina (instale o nmap antes)
nmap -sV localhost

# 5. Quem logou e quais tentativas de login houve
last -n 10
sudo grep -i "failed\|accepted" /var/log/auth.log | tail -n 20   # sem esse arquivo? use a linha de baixo
journalctl -u ssh --since "24 hours ago"    # o serviço pode se chamar sshd

# 6. Procure binários SUID
find / -perm -4000 -type f 2>/dev/null

# 7. Capture 20 pacotes de DNS enquanto roda um dig em outro terminal
sudo tcpdump -i any -n -c 20 port 53

Ao terminar, tente responder: alguma porta aberta no passo 3 te surpreendeu? Ela escuta em 127.0.0.1 (só local) ou em 0.0.0.0 (todas as interfaces, ou seja, acessível pela rede)? Essa distinção é exatamente o que separa um Redis inofensivo de um Redis exposto.

E com IA?
  • Agente que roda comandos é um processo com privilégio. Se um assistente de IA executa comandos de shell na sua máquina, vale o que você viu aqui: rode num container ou VM, com usuário próprio e sem sudo, e limite para onde ele pode se conectar.
  • Servidor de IA local também é porta aberta. Um servidor MCP (Model Context Protocol, padrão para dar ferramentas a um modelo) ou uma API de modelo rodando na sua máquina e escutando em 0.0.0.0 fica acessível para a rede. Confira com o ss -tulpn do mini-lab e prefira 127.0.0.1.
  • Log do que o agente fez. Registre quais comandos e ferramentas o agente chamou, e com quais argumentos. Sem isso, não dá para investigar depois.

Checkpoint

Qual a diferença prática entre TCP e UDP, e qual deles o DNS usa normalmente?

TCP abre conexão (three-way handshake), garante entrega e ordem; UDP só envia, sem garantia, e por isso é mais leve. A maioria das consultas DNS usa UDP na porta 53, com TCP para respostas grandes e transferências de zona.

Um cookie de sessão sem HttpOnly fica exposto a qual ataque?

A XSS: se um atacante conseguir executar JavaScript na página, pode ler document.cookie e roubar a sessão. Com HttpOnly, o script não enxerga o cookie.

Por que um binário com SUID de root é um risco?

Porque ele roda com privilégios de root mesmo quando executado por um usuário comum. Se tiver uma falha ou permitir rodar comandos, vira um caminho de escalação de privilégio até root.

Você suspeita de força bruta em SSH num servidor Ubuntu. Onde e como olha?

Em /var/log/auth.log (ou journalctl -u ssh), procurando com grep por "Failed password" e contando IPs de origem. Depois, last para ver se algum login teve sucesso, e who para ver sessões ativas.

Posso rodar nmap no site de uma empresa para praticar?

Não sem autorização por escrito. Escanear sistemas de terceiros sem permissão pode ser enquadrado como crime no Brasil (Lei 12.737/2012) e viola termos de uso. Pratique em localhost, em VMs suas, em scanme.nmap.org ou em plataformas de treino.
