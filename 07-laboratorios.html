Laboratórios gratuitos e plano de estudo

Ao fim desta página você vai saber onde praticar segurança de graça e dentro da lei, como organizar 12 semanas de estudo e o que mostrar a quem for te contratar.

A regra antes de tudo: só pratique onde você tem permissão

Segurança se aprende fazendo, mas a mesma técnica que é estudo num laboratório é crime num sistema alheio. No Brasil, a Lei 12.737/2012 (conhecida como Lei Carolina Dieckmann) incluiu no Código Penal o crime de invasão de dispositivo informático (art. 154-A), e a Lei 14.155/2021 aumentou as penas. "Só estava testando" não é defesa; a intenção de aprender não substitui autorização.

Na prática, você pode atacar:

  • máquinas, containers e contas suas, montados para isso;
  • plataformas de treino que existem justamente para serem atacadas (todas as da tabela abaixo);
  • empresas com programa de bug bounty (programa público em que a empresa autoriza testes e paga por falhas encontradas), respeitando exatamente o escopo que elas publicam.
Armadilha comum

Rodar um scanner "só para ver" no site do trabalho, da faculdade ou de um amigo. Mesmo sem má intenção, sem autorização por escrito isso pode ser enquadrado como tentativa de invasão, e no trabalho ainda pode disparar o SOC e virar incidente com o seu nome. Na dúvida, não faça.

Armadilha comum: a conta de nuvem

Criar recursos numa conta AWS, GCP ou Azure pessoal "só para estudar" e esquecer ligado. Uma máquina ou um NAT Gateway parado ali vira fatura no fim do mês. Se for inevitável usar nuvem, configure um alerta de orçamento antes de qualquer coisa e destrua tudo ao final (terraform destroy). Este guia foi montado para que você não precise.

Plano de 12 semanas

Pensado para quem trabalha como dev e tem 6 a 8 horas por semana. As quatro primeiras semanas são iguais para as duas trilhas, porque a base é a mesma; depois, escolha uma. Por que não as duas ao mesmo tempo? Porque, com pouco tempo, profundidade numa área rende portfólio e entrevista; um pouco de tudo rende só ansiedade. A outra trilha pode vir depois.

Home lab de custo zero

Um home lab é um ambiente de testes na sua própria máquina, onde você pode atacar e defender à vontade, legalmente. Tudo abaixo roda com Docker, sem nuvem. Reserve uns 8 GB de RAM livres para o Wazuh; o resto é leve.

1. Juice Shop + ZAP (AppSec e DevSecOps)

O ZAP (Zed Attack Proxy, scanner open source mantido hoje pela Checkmarx) faz DAST (Dynamic Application Security Testing, testar a aplicação rodando, de fora, como um atacante faria). O baseline scan é passivo: navega pelo site e aponta problemas sem atacar de verdade, por isso é o mais usado em CI.

# sobe o Juice Shop em http://localhost:3000
docker run --rm -d --name juice -p 3000:3000 bkimminich/juice-shop

# roda o ZAP baseline contra ele (Linux: --network host deixa o container ver o localhost)
docker run --rm --network host -v "$(pwd)":/zap/wrk:rw ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://localhost:3000 -r relatorio-zap.html

# no macOS/Windows, troque localhost por host.docker.internal e remova --network host

O relatório HTML fica na pasta atual. O próximo passo natural é colocar esse mesmo comando num workflow do GitHub Actions e fazer o pipeline falhar quando aparecer um alerta de risco alto.

2. Wazuh single-node (Blue Team)

O repositório oficial wazuh-docker traz uma configuração de nó único. Confira na página de releases do repositório qual é a versão estável mais recente e use essa tag no lugar de vX.Y.Z.

# o indexador (baseado em OpenSearch) exige este ajuste do kernel no Linux
sudo sysctl -w vm.max_map_count=262144

git clone https://github.com/wazuh/wazuh-docker.git -b vX.Y.Z
cd wazuh-docker/single-node

# gera os certificados TLS internos entre os componentes
docker compose -f generate-indexer-certs.yml run --rm generator

docker compose up -d
# painel em https://localhost (o certificado é autoassinado; o navegador vai reclamar)
Armadilha comum

A senha padrão do painel está documentada no próprio repositório, ou seja, é pública. Não exponha esse lab na internet nem na rede do trabalho, e troque as senhas se for mantê-lo ligado.

3. Sigma CLI (detecção como código)

O sigma-cli valida e converte regras Sigma. O pipx instala ferramentas Python cada uma no seu ambiente isolado, sem bagunçar o Python do sistema.

pipx install sigma-cli
sigma plugin install splunk          # backend que traduz para SPL

# valida a sintaxe (ótimo para um passo de CI)
sigma check regras/

# converte para uma busca do Splunk, sem pipeline de mapeamento de campos
sigma convert -t splunk --without-pipeline regras/ssh_bruteforce.yml

Use como ponto de partida a regra de força bruta SSH da página de Blue Team. Para outros SIEMs, liste os plugins com sigma plugin list.

Portfólio: o que mostrar

Para quem está mudando de área, o portfólio pesa mais que o diploma, porque é a prova de que você sabe fazer. E você tem uma vantagem: já sabe usar git, escrever README e montar CI. Ideias, todas sem custo de nuvem:

01

Pipeline com scans

Um repositório com app de exemplo e um workflow que roda SAST, scan de dependências, detecção de segredos, scan de imagem e ZAP baseline. README explicando o porquê de cada etapa.

02

Repositório de detecções

Regras Sigma com logs de teste (um que deve disparar, um que não deve), validação no CI e mapeamento ATT&CK num arquivo do Navigator.

03

Write-ups

Relatos passo a passo de labs e CTFs: o que você tentou, o que deu errado, como resolveu e como se defender. Escreva só sobre desafios em que a plataforma permite publicar solução.

04

Relatório de incidente simulado

Pegue um lab do CyberDefenders e escreva como se fosse um incidente real: linha do tempo, impacto, contenção e lições, no formato de postmortem.

05

Threat model de um app com IA

Pegue um app simples com LLM (um chatbot que busca em documentos, por exemplo), desenhe o fluxo de dados, aplique STRIDE e o OWASP Top 10 para LLMs e escreva as mitigações. Para ir além: uma regra Sigma que detecta abuso do agente.

Ponte com o que você já faz

Recrutadores de segurança leem um bom write-up como você lê um bom postmortem: o que importa é a clareza do raciocínio, não só o resultado. Escrever bem é um diferencial enorme na área.

Checkpoint

1. Você achou uma falha óbvia no site de uma loja onde compra. Pode testar para confirmar?

Não, a menos que a loja tenha um programa de bug bounty ou política de divulgação que autorize testes, e ainda assim só dentro do escopo publicado. Testar sem autorização pode ser enquadrado no art. 154-A do Código Penal (Lei 12.737/2012).

2. Por que preferir flaws.cloud ao CloudGoat no começo?

Porque o flaws.cloud roda na infraestrutura dos autores e não cria nada na sua conta, enquanto o CloudGoat sobe recursos na sua conta AWS, que podem gerar cobrança se você esquecer de destruí-los.

3. Por que escolher uma trilha nas semanas 5 a 12 em vez de estudar as duas?

Com 6 a 8 horas por semana, profundidade numa área gera portfólio e assunto para entrevista. A base comum das semanas 1 a 4 serve para as duas, e a segunda trilha pode vir depois.
